# Проверка идеи «точного движка»: доказывать результат, не читая всю модель

> Предложение пользователя:
> 1. эксперты = общие компоненты + точные остатки;
> 2. состояние x = U a + r: компактная часть (W U) на GPU, остаток W r читать только при необходимости;
> 3. доказательство выбора (интервалы) вместо полного расчёта;
> 4. SSD как хранилище уточнений с предсказанием загрузок.
>
> Проверено на настоящей MoE-модели **granite-3.1-3b-a800m** (Apache-2.0): 32 слоя, d=1536, 40 экспертов, выбирается 8.
> Калибровка — 4096 токенов, тест — другие 4096 (Википедия RU/EN, код Python, задачи экзамена).
> Код: `exact/probe.py`, `exact/router_gaps.py`, `exact/expert_structure.py`.

## 1. Насколько низкоранговы реальные состояния (вход MoE-блока)

| m главных направлений из 1536 | 64 | 256 | 512 | 1024 |
|---|---|---|---|---|
| энергия в остатке, слой 2 | 46% | 28% | 17% | 5.7% |
| энергия в остатке, слой 16 | 60% | 43% | 30% | 13% |
| энергия в остатке, слой 30 | 52% | 38% | 27% | 12% |

**Состояния не низкоранговые:** 64 направления — это только 40–54% энергии. Промежуточные состояния экспертов тоже: 128 направлений из 512 дают ошибку выхода ~55%.

## 2. Можно ли доказать выбор 8 экспертов по компактной части

Строгая граница: |w_i·r| ≤ ‖P⊥w_i‖·‖r‖, где P⊥w_i — часть строки, ортогональная главным направлениям.

- **Доказано — 0% токенов при любом m < 1536.** При m = 1536 (без остатка) — 100%, это проверка кода.
- Причина — выбор экспертов идёт «по лезвию». В слое 16 запас между 8-м и 9-м экспертом: медиана **0.073**, у 10% токенов меньше **0.010**. При этом разброс оценок маршрутизатора σ = 1.05.

| m | реальная ошибка оценки (медиана) | строгая граница (медиана) | набор экспертов РЕАЛЬНО меняется |
|---|---|---|---|
| 256 | 0.143 | 7.95 | у 68% токенов |
| 512 | 0.118 | 5.92 | 59% |
| 1024 | 0.081 | 2.84 | 44% |
| 1400 | 0.044 | 0.79 | 25% |

Значит, дело не только в широких границах (они в 18–55 раз шире реальной ошибки). Даже при 91% размерности приближение **на самом деле** меняет экспертов у четверти токенов. Решение маршрутизатора зависит от мелких деталей полного состояния.

## 3. Есть ли у экспертов общие конструкции (пункт 1)

| | |
|---|---|
| точное хранение bf16 с энтропийным кодированием | **10.6 бит/вес** (−33%). Старший байт (знак + 7 старших бит порядка) — 2.67 бита из 8; младший байт (младший бит порядка + 7 бит мантиссы) — 7.97 из 8, то есть мантисса практически шум |
| доля, объяснённая k общими компонентами (40 экспертов) | k=8: 22.6%; k=16: 44%; k=32: 84% — как у независимых случайных матриц (k/40) |
| нейроны двух экспертов после лучшей перестановки | |корреляция| медиана 0.082 — на уровне случайного «лучшего из 512» |
| остаток после вычитания сопоставленного нейрона | 99.3% энергии |

Общих конструкций, даже скрытых перестановкой, не найдено.

## 4. Что вообще значит «тот же ответ»

Посчитать один слой в fp32 вместо bf16 той же модели — и уже **0.7–2.3% итоговых токенов меняются** (жадный выбор). У 10% токенов запас победителя в логитах меньше 0.25.

Эталонный ответ сам по себе не единственен: он зависит от точности и от порядка сложения на конкретном железе.

## Вывод

На этой модели гипотеза «большие части данных регулярно не нужны, и это можно дёшево доказать» **не подтвердилась**:
- состояния высокоранговые;
- эксперты независимы;
- дискретные решения (выбор экспертов и итоговый токен) часто стоят на запасе в сотые доли.

Поэтому любое приближение их переворачивает, а доказательство требует почти полного расчёта.

Проверенные разложения полезного выигрыша не дали. Это **не** нижняя граница для любых других представлений, но на сегодня самая дешёвая *известная* точная единица — выбранные эксперты, прочитанные целиком.

Для GLM-5.3 это 8 из 256 маршрутизируемых экспертов (3.1% экспертных весов). Вместе с общими экспертами, вниманием и прочим активно около 40 из 753 млрд параметров (~5.3%). Сколько из этого читать с диска, зависит ещё и от кэша.

Маршрутизатор дешёвый (~0.5% умножений выбранных экспертов) и может считаться точно. Но только если его вход точный: приближение, переданное из предыдущего слоя, этим не исправить.

Без потерь можно выиграть:
- энтропийное кодирование весов (−33% для bf16, для FP8 меньше);
- кэш горячих экспертов и предзагрузку;
- RAID из NVMe;
- спекулятивное декодирование: точное распределение большой модели, проверка пачки токенов за одно чтение.

## Оговорки

- Модель маленькая (d=1536, 40 экспертов). У GLM-5.3 d=6144 и 256 экспертов. При 256 кандидатах на 8 мест запасы у границы выбора скорее ещё меньше, так что ожидать лучшего не стоит. Но проверить на крупной MoE (Qwen3-30B-A3B) было бы правильно.
- Границы взяты через нормы (Коши–Шварц). Более хитрые оценки сузили бы их, но пункт 2 показывает: даже *реальная* ошибка приближения уже меняет решения.

# Эксперимент 2: постепенное чтение битов весов с доказательством точного округления

> Гипотеза пользователя:
> 1. вычислить y = W x по части битов весов;
> 2. получить строгий интервал [L, U], содержащий результат эталонного ядра;
> 3. если round_bf16(L) = round_bf16(U), выход доказан побитово, и следующий слой получает тот же тензор — ошибки не накапливаются.
>
> Код: `exact/bitplanes.py`, сырые числа: `docs/results_exact_bitplanes.json`.

**Постановка.** gate/up шести самых нагруженных экспертов слоя 16 granite. Вход — настоящие BF16-состояния 1024 токенов, всего **3.7 млн выходов**.

Порядок чтения весов:
- сначала знак и порядок (9 бит): без них не построить границу;
- затем мантисса по одному биту, k = 0…7.

Интервал вклада недочитанных битов покоординатно точный. Ошибка накопления FP32 эталонного ядра учитывается строго, для любого порядка суммирования: (n−1)·2⁻²⁴·Σ|w x|. Отдельно посчитан «идеальный» случай без неё.

| прочитано бит мантиссы (из 7) | 0 | 1–5 | 6 | 7 (всё) |
|---|---|---|---|---|
| доказано выходов, строго | 0% | 0% | **0%** | 30.6% |
| доказано выходов, «идеально» (без ошибки накопления) | 0% | 0% | **0%** | 100% |

- **Побитовая проверка:** из 1.14 млн доказанных выходов расхождений с настоящим BF16-ядром PyTorch — **0**. Метод корректен.
- **Пропустить не удалось ни одного бита.** Если не дочитать даже последний бит мантиссы, не доказывается ни один выход. Среднее чтение — 16 бит на вес из 16.
- Даже при полностью прочитанных весах строгая проверка проходит лишь у 31% выходов. Для остальных интервал ошибки FP32-накопления сам пересекает границу округления. Побитовое совпадение там требует воспроизвести точный порядок сложения конкретного ядра.
- Проверка заняла в 48 раз больше времени, чем само умножение (неоптимизированный CPU-код).

**Почему так.** Неопределённость выхода от недочитанных битов ≈ 2^-(k+1)·Σ|w x|. Клетка округления выхода ≈ 2^-9·|y|. Из-за взаимного погашения слагаемых Σ|w x| в десятки раз больше |y| (n = 1536 слагаемых разных знаков).

Выход хранится с той же точностью, что и веса (BF16 → BF16), поэтому для точного выхода нужна даже *бо́льшая* точность входа, чем записано. Лишних битов в весах нет. У FP8 (E4M3, официальный формат GLM-5.3) мантисса — 3 бита, запаса ещё меньше.

**Вывод.** Обе гипотезы «читать меньше без потерь» опровергнуты:
- подпространство состояний (эксперимент 1);
- битовые плоскости (эксперимент 2).

Для точного исполнения остаются известные инструменты:
- поток выбранных экспертов целиком;
- энтропийное сжатие без потерь (−33% для BF16, для FP8 меньше);
- кэш и предзагрузка;
- спекулятивное декодирование (точное распределение большой модели при проверке пачки токенов);
- **детерминированное ядро** с фиксированным порядком суммирования — иначе само понятие «тот же ответ» не определено (см. шумовой порог 0.7–2.3%).
